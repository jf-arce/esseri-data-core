Objective: Deliver the approved family-facing billing slice with server-enforced visibility limited to the economic-responsible family recorded on each invoice.

## Specs

- **S1 — Original objective (verbatim):** `como podemos dejar 100 productivo el portal de familia`.
- **S2 — Approved first slice:** The user approved with `dale` the immediately preceding proposal for family billing: `facturas, vencimientos, cuenta corriente, pagos y comprobantes`. Acceptance: the portal displays invoices, due dates, movements linked to those invoices, recorded payments, and available receipt downloads. **Assumption:** this slice is read-only; it does not initiate or register payments.
- **S3 — Approved privacy boundary:** The user replied `ok` to the recommendation: `solo el responsable económico vea las facturas, pagos y movimientos asociados a esas facturas`. Acceptance: derive the family from the authenticated identity and authorize each invoice via its persisted `responsable_economico_id` → `familia_id`; expose only that family’s invoice-linked financial records and receipts, never another linked family’s data. Verify own-family, non-economic linked-family, and unauthenticated cases through public API behavior.
- **S4 — Reported integrated-admission failure (verbatim):** `FOR UPDATE cannot be applied to the nullable side of an outer join` while calling `POST /inscripciones/solicitudes/.../alta-integrada`. Acceptance: finalizing an approved admission locks only the `alumno` row when checking whether the aspirant already exists, so PostgreSQL does not attempt to lock the nullable joined `persona` side.
